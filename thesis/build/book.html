Abstract

CineMax Karachi is a web-based cinema ticketing system that lets customers in Karachi choose exact seats on a live seat map, pay, and receive a QR-coded e-ticket, while staff run shows, prices, refunds and door check-in from an administration panel. The project re-engineered a minimal academic PHP application, which had no seat model and was open to SQL injection, into a seat-level booking platform on the same low-cost stack: plain PHP, MariaDB 10.4 and server-rendered pages.

The central problem in ticketing is preventing two customers from buying the same seat. We solve it in three layers: five-minute seat holds stored in the database, a UNIQUE (show_id, seat_label) key on both held and sold seats so the database itself refuses a duplicate claim, and a single InnoDB transaction for each booking. Tickets carry an HMAC-signed verification link, so any phone can recognise a forged code. Other features include show scheduling with clash detection, simulated card, JazzCash and Easypaisa payment, a time-based refund policy, a camera ticket scanner, a TMDB-fed catalogue and an analytics dashboard.

Evaluation on Docker showed that in 21 rounds of ten simultaneous requests for the same seat, exactly one request won every time. All 22 business-rule unit checks and all 27 ticket-authenticity checks passed, and public pages answered within 112 ms at the 95th percentile with ten concurrent clients. Plain-text password storage and the simulated payment gateway remain the main limitations.

Keywords: online ticket booking, seat reservation, concurrency control, database transactions, PHP, MariaDB, QR code, web application security

Chapter 1

Introduction

This chapter explains why CineMax Karachi was built and states its problem, objectives and scope. Chapters 2 to 7 then cover the literature, requirements, design, implementation, evaluation and conclusions.

1.1 Background

Karachi's cinemas screen Hollywood, Bollywood and Lollywood films in multiple halls, with multiple show times each day. Buying a ticket has traditionally meant queuing at the box office or using a chain's own website. Box-office sales give no view of seat availability, cause long queues on release weekends and tie up staff who print tickets by hand.

Online sales solve these problems only when they rest on a reliable model of shows, individual seats and payments. A system that merely records "three tickets for the evening show" cannot show which seats remain, cannot stop two customers from receiving the same seat and cannot be checked at the door. Widely taught, low-cost technologies (PHP, a MySQL-compatible database and small JavaScript libraries) already provide transactions, integrity constraints and interactive pages. This project tests whether they are sufficient to build a ticketing system whose core guarantee, that no seat is ever sold twice, holds under concurrent load.

1.2 Starting point and problem statement

The project began from an existing student-template "Online Movie Booking System" written in plain PHP and MySQL. An audit of that baseline found that it had no shows or seats (a booking was one row holding a seat count), no concurrency control, SQL built by string interpolation, passwords and card numbers stored in plain text, admin pages that did not all check for a logged-in administrator, and functional defects such as a price-edit query without a WHERE clause. We kept its technology and its original database dump, and evolved the system through numbered, re-runnable migrations.

Problem statement. Design and implement a secure, seat-level online cinema booking system on a conventional PHP and MySQL stack that guarantees no seat is sold twice under concurrent access, and that supports the full ticket lifecycle from discovery to check-in and refund.

Chapter 2

Literature Review

This chapter reviews existing booking systems, the architecture and technologies available, and the theory of concurrency control and web security on which the design rests. It closes with the gap the project addresses.

2.1 Ticketing as a problem domain

A cinema ticket sells access to a perishable, capacity-limited resource: a seat for the 18:30 show is worth nothing after 18:30, and each seat can be sold exactly once. Unlike ordinary e-commerce stock, the unit is specific (seat E6), so an oversold seat cannot be fixed by back-ordering. Reservation systems therefore share a known structure (Fowler, 2002; Kleppmann, 2017): discrete inventory attached to a timed event, slow interactive selection, fast but atomic commitment, and sharp contention on release days. The standard response to slow selection followed by fast commitment is a temporary hold, which sets seats aside for a fixed period during checkout and returns them to sale if the customer leaves. CineMax Karachi uses a five-minute hold.

2.2 Existing solutions

We compared categories of system rather than named products, whose features change between releases and whose internals are not public. Global aggregators (for example BookMyShow and Fandango) and chain websites run on proprietary cinema-management software that a small venue cannot license or host. Local marketplaces support JazzCash and Easypaisa but depend on each cinema exposing its inventory. Academic PHP projects are free to run; the one this project inherited recorded a booking as one row with a seat count, concatenated request values into SQL and stored passwords in plain text.

2.3 Architecture and technologies

Web applications conventionally use three tiers: browser, application server and database (Sommerville, 2016). We chose server-side rendering, where each URL returns a complete HTML page, over a single-page application, because it needs no separate API layer or JavaScript build chain and is simpler to secure and host. Small JSON endpoints are added only where interaction requires them: seat holds, seat-status polling, live search, promo validation and OTP issue. In Fowler's (2002) terms, the code uses Page Controller (one script per page), Transaction Script (procedures such as finalize_booking() own one business operation each) and Template View, with Post/Redirect/Get on every form.

2.4 Concurrency control

The naive booking algorithm is check-then-act: if seat E6 is free, record E6 as sold. If two requests read before either writes, both sell the seat, a lost-update anomaly (Berenson et al., 1995). Wrapping the sequence in a transaction does not help on its own, because a plain read under InnoDB's default REPEATABLE READ isolation takes no lock (Silberschatz, Korth and Sudarshan, 2019). Three standard remedies exist (Elmasri and Navathe, 2016; Kleppmann, 2017):

  1. Pessimistic locking: lock the row before checking it, for example with SELECT ... FOR UPDATE.

  2. Optimistic control: detect conflicts at commit time with a version column and retry.

  3. Constraint-based exclusion: let a UNIQUE key reject the second insert of the same (show, seat) pair, collapsing check and act into one atomic operation.

The third is the most robust for seats, because the invariant "at most one sale per seat per show" maps exactly onto a unique key and stays correct even if a future code path forgets to lock. CineMax Karachi uses it as the primary guarantee, with FOR UPDATE locks as a secondary measure inside the payment transaction. Holds are leases (Gray and Cheriton, 1989): each carries an expiry time, and expired holds are treated as free, so an abandoned checkout needs no clean-up protocol.

2.5 Web application security

The OWASP Top 10 (OWASP Foundation, 2021) names the risks most relevant here: broken access control (opening another customer's ticket or an unguarded admin page), cryptographic failures (plain-text passwords, stored card numbers), injection, insecure design (double booking, refund abuse) and misconfiguration (executable upload folders). The standard controls are prepared statements against SQL injection (Halfond, Viegas and Orso, 2006), contextual output encoding against cross-site scripting, synchroniser tokens against cross-site request forgery (Barth, Jackson and Mitchell, 2008), and extension allow-lists, content checks and non-executable upload folders against malicious uploads.

A QR code (ISO/IEC 18004) should carry an opaque identifier rather than personal data, and validity must be decided by the server at scan time so that a copied code is admitted once. Signing the identifier with a key held only by the server, using a message authentication code such as HMAC, also lets anyone recognise a code the cinema never issued. For usability, Nielsen's (1994) heuristics motivated the visible hold countdown, disabled sold seats and plain-language error messages.

2.6 Research gap

Commercial platforms prevent double booking but are proprietary and costly; affordable academic systems omit the seat model and are insecure. The literature supplies the techniques to close the gap: constraints and transactions for correctness, leases for abandoned checkouts, prepared statements and synchroniser tokens for security, and server-validated, signed identifiers for admission. CineMax Karachi applies them to a framework-less PHP and MariaDB stack and measures whether the guarantee holds under concurrent load.

3.4 Use cases

The use-case model has 19 use cases: browsing, search, film details, registration and sign-in for guests and customers (UC-01 to UC-05); seat selection, checkout, e-ticket, history, cancellation and reviews for customers (UC-06 to UC-11); catalogue, show scheduling, promotions, refunds, scanning, reports and user moderation for administrators (UC-12 to UC-18); and catalogue seeding for the operator (UC-19). The central use case is described in full below.

UC-06/07: Book tickets. Preconditions: the show is Active and has not started, and prices are set for the film.

  1. The system displays the seat map with current seat states and class prices.

  2. The customer selects one to ten free seats and presses Continue.

  3. The system validates the seat labels, releases the customer's earlier holds and inserts a five-minute hold for each seat.

  4. Checkout shows a countdown; the customer adds snacks and optionally a promo code.

  5. The customer chooses a payment method and enters details.

  6. In one transaction the system re-reads the customer's unexpired holds with a lock, re-validates the promo code, inserts the booking and its seats and snacks, increments promo usage, adds loyalty points and deletes the holds.

  7. The system commits and shows the e-ticket with its QR code.

Extensions: 3a. a seat is already held or sold: the whole hold is rolled back and the conflicting seats are named. 4a. the countdown reaches zero: the customer returns to the seat map. 5a. invalid payment details: the form is shown again and the hold continues. 6a. the hold expired or a seat insert violates the unique key: the transaction rolls back and the customer is told why. Postcondition: exactly one booking exists with status Booked, and its seats can no longer be selected by anyone.

Chapter 4

System Design

CineMax Karachi is a server-rendered, three-tier web application. Browsers talk HTTP to Apache and PHP, PHP talks to a single MariaDB database, and an offline command-line seeder talks to the TMDB API. This chapter presents the architecture, the data model, the booking workflow and state machine, and the main design decisions.

4.1 Architecture

Figure 4.1: Runtime architecture. Browsers call page controllers and AJAX endpoints over HTTP; all of them reach MariaDB through the helper layer, and only the command-line seeder talks to TMDB.

Two web applications share one database and one helper layer. The customer site consists of page controllers such as seat_map.php, checkout.php, payment.php and ticket.php. The admin panel (Admin/) has one page per feature, and every page starts with include('auth.php'), which redirects to the login page unless an administrator is signed in. The helper layer (includes/) holds all shared logic: functions.php for database access, escaping, CSRF tokens and flash messages, and booking.php for the booking domain. Five AJAX endpoints return JSON for the seat map, live search, promo codes and OTPs.

The code follows a consistent layering without a framework. A controller block at the top of each page reads the request, checks authentication, CSRF token and ownership, calls domain functions, and then either redirects or renders. Because no HTML is output before that block finishes, every form can follow Post/Redirect/Get.

4.2 Database design

The database has 21 InnoDB tables: 10 inherited from the baseline dump and 11 added by migration. Figure 4.2 shows the entities and relationships.

Figure 4.2: Entity-relationship diagram. addmovie is the hub of the catalogue and shows the hub of inventory; the two highlighted tables carry the UNIQUE (show_id, seat_label) keys that prevent double booking.

The two unique keys state the system's main invariant, at most one claim per seat per show, in a form the database enforces on every insert. The new tables are in third normal form, with one deliberate exception: a booking keeps text copies of the film, cinema, date and prices at the time of sale, as an invoice does, so tickets and reports stay accurate after catalogue edits.

The original dump dbmo.sql is never edited. Changes are numbered SQL files in database/migrations/ that use ADD COLUMN IF NOT EXISTS, CREATE TABLE IF NOT EXISTS and guarded inserts, so any migration can safely be run again. Migration 001 also back-filled totals, references and user links for legacy bookings.

4.3 Seat model

A hall is a grid of total_rows × seats_per_row seats (8 × 12 = 96 by default), labelled A1 to H12. A seat's class depends only on its row: A to C are Economy, D to F Business and G onwards First. A seat's state for a show is derived at read time rather than stored: sold if a booking_seats row exists, held if an unexpired seat_holds row exists, and free otherwise. With no separate status column, the displayed state cannot drift out of step with the two tables.

4.4 Booking workflow

Figure 4.3: Booking sequence. Solid arrows are requests, dashed arrows replies; the two highlighted writes are where a unique key can refuse a seat.

The workflow has three phases with different consistency needs:

  1. Selection (no writes). The browser polls seat status every ten seconds and disables taken seats, but nothing is reserved, so customers who are only looking lock nothing.

  2. Hold (short transaction). Continue deletes the customer's earlier holds and inserts one hold per seat. Any failed insert, including a unique-key violation caused by a concurrent customer, rolls back the whole hold: the customer gets all requested seats or none.

  3. Commit (one transaction). On payment, finalize_booking() re-reads the customer's unexpired holds FOR UPDATE, re-validates the promo code, writes the booking, seats, snacks, promo usage and loyalty points, deletes the holds and commits. The booking_seats unique key is the final guard.

4.5 Booking state machine

Figure 4.4: Booking state machine. A booking leaves the Booked state exactly once, at the door or by cancellation; a cancelled booking then waits for an administrator's refund decision.

Every transition is a conditional UPDATE whose WHERE clause repeats the expected starting state, for example WHERE booking_ref = ? AND status = 'Booked'. The affected-row count tells the code whether the transition happened, so two concurrent attempts, such as a scan and a cancellation of the same ticket, cannot both succeed.

4.6 Interface design

Both sites share a light theme of white cards on a light grey page, with the brand's pink-to-coral gradient for actions and status badges that pair a dark label with a pale tint. Seats are <button> elements with an aria-pressed state, coloured by class, green when selected, orange when held by others and grey when sold. The light theme is applied as override stylesheets, so the purchased dark templates are never edited.

Chapter 5

Implementation

This chapter describes how the system was built: the development method, the helper layer, and the modules that implement the booking lifecycle. Code excerpts are shortened where marked with .... Screenshots were taken on 13 October 2026 from the Docker deployment with the TMDB catalogue and demonstration data.

5.1 Development method and tools

We used an incremental model: every increment delivered a working, demonstrable slice of the booking flow, so the site never stopped working and defects could be traced to a small change. A foundation step (schema contract, migration 001 and the helper layer) was followed by five booking phases (shows and seat map; checkout and payment; e-ticket and scanner; history, cancellation and refunds; dashboard, reports and search), with administration and account pages built in parallel, then TMDB integration and hardening.

Two practices let the developers change one codebase in parallel. File ownership in TEAM_NOTES.md assigns every file to one owner; a developer who needs a change in someone else's file writes a numbered request instead of editing it. A schema contract (database/SCHEMA_CONTRACT.md) defines every table, column and business rule, and wins over code if the two disagree. Work was shared through Git and GitHub, and database changes were delivered only as new migration files. Development used Docker Compose and XAMPP; testing used cURL, Playwright and ApacheBench. The application consists of 9,725 lines of PHP in 86 files, excluding vendored templates and libraries.

5.2 The helper layer

Every new page includes includes/functions.php, which opens the database connection, starts the session, and sets both PHP and the MySQL session to the Asia/Karachi time zone. Aligning the clocks matters because holds expire by SQL NOW() while refund quotes use PHP time(); in the UTC Docker container, a show would otherwise be judged five hours wrong.

db_query() is the single entry point for parameterised SQL: it prepares the statement, binds typed parameters and returns a result set for reads, the affected-row count for writes, or false on failure. Returning the affected-row count is what makes the guarded state transitions of Section 4.5 possible. The codebase makes 220 calls through this wrapper and its db_one() and db_all() variants. e() escapes all output with htmlspecialchars(..., ENT_QUOTES, 'UTF-8'), and CSRF tokens are 128 random bits stored in the session and compared with hash_equals():

function csrf_token()
{
    if (empty($_SESSION['csrf'])) {
        $_SESSION['csrf'] = bin2hex(random_bytes(16));
    }
    return $_SESSION['csrf'];
}

function csrf_ok()
{
    return isset($_POST['csrf']) && hash_equals(csrf_token(), (string) $_POST['csrf']);
}

5.3 Catalogue, shows and the seat map

Figure 5.1: Home page. The slider shows the most popular current films from TMDB with rating, genre, runtime and a Book Now button.

The movie browser filters by whitelisted genre, language and cinema parameters and offers live search, which escapes SQL LIKE wildcards and returns at most six suggestions. upcoming_shows() lists a film's active shows for the next seven days with seats left computed in the same query; TIMESTAMP(show_date, show_time) > NOW() hides a show the moment it starts, and every booking step re-checks the show with bookable_show().

The seat map renders each seat as a button whose state comes from seat_states(), which first deletes expired holds and then returns booked, held-by-others and held-by-me lists. The page polls that state every ten seconds and deselects any seat someone else has taken. Polling is a usability feature, not a correctness mechanism: the server, not the display, refuses a taken seat.

Figure 5.2: Seat map. Sold seats are grey with a cross, orange seats are held by another customer, and green seats are this customer's selection; the summary totals the selection by class.

5.4 Seat holds

Continue posts the selection to ajax/seat_hold.php, which checks sign-in, show status, prices, the 10-seat limit and every seat label, returning a specific HTTP status for each failure (401, 404, 422) and 409 with the conflicting seats. The hold itself is one transaction:

function hold_seats($show_id, $user_id, $labels)
{
    release_expired_holds();
    mysqli_begin_transaction(db());
    db_query('DELETE FROM seat_holds WHERE user_id = ?', 'i', [(int) $user_id]);
    $conflicts = [];
    foreach ($labels as $label) {
        $booked = db_one('SELECT 1 FROM booking_seats WHERE show_id = ? AND seat_label = ?', ...);
        $inserted = $booked ? false : db_query(
            'INSERT INTO seat_holds (show_id, seat_label, user_id, expires_at)
             VALUES (?, ?, ?, NOW() + INTERVAL 5 MINUTE)', 'isi', [...]);
        if (!$inserted) {
            $conflicts[] = $label;
        }
    }
    if ($conflicts) {
        mysqli_rollback(db());
        return $conflicts;
    }
    mysqli_commit(db());
    return [];
}

Three properties matter. Deleting the customer's earlier holds first gives each customer one active selection. When two customers race for the same seat, both may pass the booking_seats check, but only one INSERT can succeed because of UNIQUE (show_id, seat_label); the loser's seat is reported as a conflict. Any conflict rolls back the whole transaction, so a failed attempt leaves the customer exactly where they were. Expired holds are deleted at the start of every seat read and hold attempt, so a seat frees itself for the next reader without a scheduler.

5.5 Checkout and payment

Checkout recomputes every price on the server; the browser's totals are only a preview. Snack quantities are clamped to 0 to 10 and must name active snacks, and the discount is floored so the cinema never gives away more than the advertised percentage. For example, seats E6 and E7 (Business, PKR 1,400 each) and G3 (First, PKR 2,000) plus one soft drink (PKR 250) give PKR 5,050; promo EID20 takes PKR 1,010, for a total of PKR 4,040. A countdown badge shows the remaining hold time.

Figure 5.3: Checkout. Snacks are added with quantity buttons and promo code EID20 takes 20% off; the badge counts down the hold.

Payment is simulated but validated like a real gateway. For card, the server checks a 16-digit number, a future MM/YY expiry and a 3 or 4 digit CVV, and keeps only the last four digits. For JazzCash and Easypaisa, it checks a Pakistani mobile number (^03[0-9]{9}$) and a six-digit one-time password generated with random_int(), valid for five minutes and compared with hash_equals(). In this demonstration build the OTP is displayed on screen in place of an SMS.

5.7 E-tickets and signed QR codes

The ticket page renders only for the booking's owner; any other reference shows "Ticket not found", the same message as for a reference that does not exist. The ticket lists the film, hall, seats, snacks, discount, total and masked payment (for example Card ****4242), and prints on its own through a print stylesheet.

Figure 5.4: E-ticket. The ticket lists the show, hall, seats, snacks, discount and payment, and carries the signed QR code.

An early version encoded only the reference in the QR code, so anyone could print a code with a made-up reference. The final version encodes a link to a public verification page carrying the reference and an HMAC-SHA256 signature, computed with a 64-character secret held only on the server and shortened to 24 hexadecimal characters (96 bits):

function ticket_signature($ref)
{
    return substr(hash_hmac('sha256', strtoupper(trim((string) $ref)), ticket_secret()), 0, 24);
}

Scanning the code with any phone camera opens verify.php, which shows Genuine ticket, Already used, Cancelled ticket, Show date has passed or Not a valid CineMax ticket. It masks the customer's name and shows no email, phone or price, and it reveals nothing when the signature is wrong, so references cannot be enumerated. Verification is read-only; only the admin scanner admits a ticket.

Figure 5.5: Verifying a ticket with an ordinary phone. Left: a genuine ticket, with the name masked. Right: the same link with one signature character changed is rejected.

5.8 Cancellation, refunds and the ticket scanner

The refund quote is a pure function of the booking and the current time: 100% if the show starts in 24 hours or more, 50% if it starts sooner, and no cancellation once it has started. Cancelling runs one transaction whose UPDATE is guarded by status = 'Booked'; it then deletes the booking's seat rows, which returns the seats to sale immediately, and deducts the loyalty points. Administrators approve or reject pending refunds with updates guarded by refund_status = 'Pending', so no refund can be processed twice; a rejection records a reason that the customer sees.

The admin scanner reads QR codes from the device camera with html5-qrcode, or accepts a typed reference. The server first checks the signature, then admits the ticket with one atomic UPDATE ... SET status = 'Used' WHERE booking_ref = ? AND status = 'Booked', so two staff scanning the same ticket cannot both get VALID.

5.9 Administration panel

Every admin page and delete handler starts with include('auth.php'), which redirects and exits unless an administrator is signed in. Catalogue pages share one pattern: an add form, a list with edit and delete, CSRF-protected submissions, flash messages and an activity-log entry for every change. Deleting a cinema or film that still has shows is refused with an explanation. Show scheduling rejects a second show in the same hall at the same date and time, and a show with bookings can only be cancelled, not deleted. Every upload passes through admin_upload_image(), which enforces a 2 MB limit and an extension allow-list, confirms the real image type with getimagesize(), and saves the file under a random name; the profile-photo folder also denies script execution.

Figure 5.7: Admin dashboard. Revenue, tickets, bookings, cancellations, refunds, users and today's bookings, with quick links.

The dashboard computes its tiles in one aggregate query and draws four Chart.js charts (seven-day net revenue, top films, seat-class split and booking status). Reports filter by date range, film and cinema and export CSV; each cell starting with =, +, - or @ is prefixed with a quote so a hostile customer name cannot run as a spreadsheet formula.

5.10 TMDB catalogue seeder and deployment

database/seed_tmdb.php runs only from the command line and only with --yes. It fetches 16 now-playing English-language films released in the last 120 days, 8 Hindi films from the last 150 days and 6 Pakistani films from the last three years, downloads posters and backdrops, and stops without touching the database if fewer than three films arrive. It then replaces the catalogue in one transaction: films are mapped to industries, priced in three tiers by popularity rank (Economy PKR 1,500 for the top 5, 1,200 for ranks 6 to 15 and 1,000 for the rest), and given four shows (top 10) or three shows over the next seven days. All network work happens before the transaction, so a TMDB outage leaves the database unchanged. Our run produced 30 films (16 Hollywood, 8 Bollywood, 6 Lollywood), 8 coming-soon titles and 112 shows across 9 cinemas.

Deployment is two Docker Compose services: web (php:7.4-apache with mysqli, the repository mounted live) and db (MariaDB 10.4, initialised from dbmo.sql on first start). config.php reads the database host from DB_HOST, so the same code runs in Docker and in XAMPP. docker compose up -d --build starts the whole system; Appendix A gives the full steps.

6.5 Performance

ApacheBench ran inside the web container to remove network effects, sending 200 requests per page with one client and then with ten concurrent clients. Pages that need a login reused one session cookie.

Figure 6.1: 95th-percentile latency at ten concurrent clients. All six public pages stay well under the 200 ms target; the three pages over it were tested with one shared session cookie.

Public pages served 130 to 176 requests per second, 4.8 to 5.9 times their single-client throughput, and the seat-status poll served 298 requests per second, enough for 2,980 customers polling every ten seconds on one host (298 × 10). The three slower pages were tested with a single shared session, and PHP's file-based session lock serialises concurrent requests from one session. Real customers each have their own session, so this reflects the test setup, not a capacity limit; calling session_write_close() early on read-only pages would remove it. The data set held 26 bookings and 112 shows, so these figures measure relative cost on one host, not production capacity.

6.6 Usability

The booking flow takes five transitions from film page to e-ticket, meeting NFR-07. The seat map shows a live total, checkout shows a hold countdown that turns red in the final minute, taken seats are disabled before a click, and conflicts produce specific messages. Seats are buttons with aria-pressed and the countdown is an ARIA live region. Two accessibility gaps remain: held and selected seats are distinguished by colour alone, and seat buttons lack descriptive labels such as "Seat E6, Business, available".

Chapter 7

Conclusion

This project set out to build a seat-level online cinema booking system for Karachi, on a conventional PHP and MariaDB stack, that never sells a seat twice. CineMax Karachi delivers the full ticket lifecycle. Customers browse films imported from TMDB, select exact seats on a live map, pay through a simulated card, JazzCash or Easypaisa step, and receive an e-ticket with an HMAC-signed QR code. Staff schedule shows with clash detection, manage prices and promotions, approve or reject refunds, admit customers with a camera scanner and track sales on a dashboard with CSV reports.

The central contribution is the concurrency design: five-minute seat holds stored in the database, a UNIQUE (show_id, seat_label) key on both held and sold seats, and one InnoDB transaction per booking. The evaluation confirmed it: in 21 rounds of ten simultaneous requests for one seat, exactly one request won every round. All 22 unit checks and all 27 ticket-authenticity checks passed, and public pages answered within 112 ms at the 95th percentile with ten concurrent clients.

Nine of the ten objectives were fully met. Objective O9 was partly met, and five changes are required before the system takes real payments: password storage with password_hash(), CSRF tokens on the checkout and payment requests, session-id regeneration at customer sign-in, login throttling, and integration of a real payment gateway.

The project also shows that an inherited codebase can be improved without a rewrite. The original database dump was never edited, every schema change was a re-runnable migration, a 145-line helper layer supplied prepared statements, output escaping and CSRF protection, and file ownership let the team work in parallel. With the five changes above in place, CineMax Karachi gives a small Karachi cinema reliable online, seat-level booking on low-cost hosting.

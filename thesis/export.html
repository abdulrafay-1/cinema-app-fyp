Abstract

CineMax Karachi is a web-based cinema ticketing system that lets customers in Karachi browse current films, choose an exact seat on a live seat map, pay, and receive a QR-coded e-ticket, while cinema staff run the whole operation from an administrative panel. The project began as a minimal academic PHP application with a flat booking table, string-built SQL queries and no notion of individual seats. We re-engineered it into a show-based, seat-level booking platform without changing its core technology: plain PHP, MySQL-compatible MariaDB 10.4 and server-rendered HTML.

The central technical problem in any ticketing system is preventing two customers from buying the same seat. We solve it with a three-layer design. First, selected seats are placed in a seat_holds table for five minutes. Second, a composite UNIQUE (show_id, seat_label) key on both seat_holds and booking_seats makes the database itself refuse a duplicate claim, so correctness does not depend on application timing. Third, the booking is written inside a single InnoDB transaction that either commits the booking, its seats, snacks, promotion usage and loyalty points together, or rolls all of them back.

Around this core the system provides show scheduling with clash detection, three seat classes priced per film, snacks, promotional codes, a simulated payment step for card, JazzCash and Easypaisa with a one-time password, e-tickets carrying a QR code, a camera-based ticket scanner for check-in, cancellation with a time-based refund policy (100% at least 24 hours before the show, 50% after that), loyalty points, reviews, favourites and an analytics dashboard with CSV reports. The film catalogue is populated from The Movie Database (TMDB) API by a command-line seeder that runs inside a single transaction. Security controls include prepared statements, output escaping, CSRF tokens, session-gated administration and validated image uploads.

We evaluated the system on the project's Docker environment (PHP 7.4, Apache, MariaDB 10.4.34). Twenty-two unit checks of the business rules passed. In a concurrency test, ten authenticated users requested the same seat at the same instant for 20 rounds (200 requests), and every round produced exactly one successful hold. End-to-end booking, check-in, re-scan rejection, cancellation and authorisation tests behaved as specified. With ten concurrent clients, public pages served 130 to 176 requests per second with 95th-percentile latency between 70 and 112 ms. The evaluation also documents known limitations, chiefly plain-text password storage and a simulated payment gateway, and the report sets out a roadmap to address them.

Chapter 1: Introduction

This chapter sets out why CineMax Karachi was built, the problem it solves, the objectives we committed to, the boundaries of the work and how the rest of the report is organised.

1.1 Background

Cinema-going in Pakistan has recovered strongly since the revival of multiplex cinemas in the major cities, and Karachi, as the country's largest city, hosts the densest concentration of screens. Chains such as Nueplex, Cinepax, Atrium and Capri operate halls across districts that range from Saddar and Clifton to DHA and Bahria Town. A typical cinema shows a mix of Hollywood releases, Bollywood films and local Lollywood productions, often in several halls and at five or more show times per day.

For the customer, buying a ticket has traditionally meant either queuing at the box office or using a cinema chain's own website. Box-office sales give the customer no view of seat availability before arrival, cause long queues on release weekends and opening nights, and tie up staff who must hand-write or print tickets. Online sales solve these problems only when they are built on a reliable model of individual seats, shows and payments. A system that merely records "three tickets for the evening show" cannot tell a customer which seats remain, cannot stop two customers from receiving the same seat, and cannot be checked at the door.

Web technology has made this kind of system accessible to small teams. A relational database such as MySQL or MariaDB provides transactions and integrity constraints. A server-side language such as PHP renders pages and enforces business rules. Small JavaScript libraries supply interactive seat maps, charts and QR codes in the browser. Public APIs such as The Movie Database (TMDB) supply posters, synopses, trailers and release dates that would otherwise have to be typed in by hand. The project's thesis is that these widely taught, low-cost technologies are sufficient to build a ticketing system whose core guarantee, that no seat is ever sold twice, holds under concurrent load.

1.2 The starting point: a legacy academic system

The project did not start from an empty repository. It started from an existing "Online Movie Booking System", a small PHP and MySQL application of the kind commonly circulated as a student template. Its initial commit (5 October 2026 in our repository) contained a public site with movie listings by industry (Hollywood, Bollywood, Lollywood) and an admin panel for managing lookup tables such as cinemas, genres, languages and dates.

An audit of that baseline found the following properties, which shaped every later design decision:

  • No shows or seats. A booking was a single row in booking_details that stored the movie name, cinema, date and price tier as copied text, plus a seat count. There was no concept of a scheduled show or of an individual seat.

  • No concurrency control. Because seats did not exist, nothing could prevent overselling a hall.

  • SQL built by string interpolation. Values from $_GET, $_POST and $_SESSION were inserted directly into SQL strings, which exposes the application to SQL injection.

  • Sensitive data in plain text. Passwords and full card numbers were stored as entered.

  • Weak administration security. Only some admin pages checked for a logged-in administrator, and several delete handlers could be called directly by URL.

  • Functional defects. For example, the seat-price edit form issued an UPDATE without a WHERE clause, so editing one film's prices overwrote every film's prices.

We kept the baseline's technology (plain PHP, MySQL-compatible database, Bootstrap templates) and its original database dump (dbmo.sql) intact, and evolved the system through numbered, re-runnable migrations. This decision is discussed in Chapter 4.

1.3 Problem statement

Cinema customers in Karachi need a way to see real seat availability for a specific show, reserve exact seats, pay and receive a ticket that can be verified at the entrance, without visiting the box office. Cinema operators need a way to schedule shows, set prices, sell add-ons, process cancellations and refunds fairly, verify tickets at the door and measure sales. The baseline system could do none of these reliably: it had no seat model, could not prevent double booking, could not issue verifiable tickets, and was insecure against common web attacks.

Stated as a single problem: design and implement a secure, seat-level online cinema booking system on a conventional PHP and MySQL stack that guarantees no seat is sold twice under concurrent access, and that supports the full ticket lifecycle from discovery to check-in and refund.

1.4 Motivation

Three considerations motivated the project.

  1. A real, local need. Seat-level online booking is still not universal among Karachi's cinemas, especially single-screen and smaller venues. A system that runs on inexpensive shared hosting or a single Docker host lowers the barrier for such venues.

  2. A concrete computer-science problem. Double booking is a textbook instance of a race condition on a shared resource. Solving it correctly exercises database constraints, transactions, isolation and lock behaviour, which are central topics in the Database Systems and Operating Systems courses of the degree.

  3. Software-engineering practice. Working on an inherited codebase as a team of developers is closer to industry reality than a greenfield exercise. It required us to audit legacy code, introduce migrations, document a shared schema contract and divide file ownership.

Chapter 2: Literature Review and Background

This chapter reviews the kinds of cinema booking systems already in use, the architectural patterns and technologies available to build one, and the theory of concurrency control and web security on which our design rests. It closes by identifying the gap that CineMax Karachi addresses.

2.1 Online ticketing as a problem domain

An online ticketing system sells access to a perishable, capacity-limited resource. A seat for the 18:30 show has value only until 18:30, and each seat can be sold exactly once. These two properties distinguish ticketing from ordinary e-commerce. In a typical online shop, stock is fungible (any unit of a product will do) and oversell can be fixed later by back-ordering. In ticketing, the customer chooses a specific unit (seat E6), and an oversold seat cannot be fixed after the fact without disappointing a customer in front of the screen.

The domain therefore has a well-known structure, described in practitioner literature on reservation systems (Kleppmann, 2017; Fowler, 2002):

  • Inventory is a set of discrete, identifiable units (seats) attached to a time-bound event (a show).

  • Selection is interactive and slow: customers look at a seat map, change their minds and compare prices.

  • Commitment is fast but must be atomic: once payment succeeds, the seats, the order and the payment record must all be saved, or none of them.

  • Contention peaks sharply on release days, when many customers compete for the same central seats at the same moment.

The standard response to slow selection followed by fast commitment is a temporary hold (also called a lease or soft reservation): the system sets the selected seats aside for a short time so the customer can pay without losing them, and returns them to sale automatically if the customer abandons the purchase. Every major consumer ticketing platform exposes this as a visible countdown during checkout. CineMax Karachi adopts the same pattern with a five-minute hold.

2.2 Existing solutions

We surveyed the categories of booking systems available to a Karachi cinema-goer and to a small cinema operator. We describe categories rather than ranking named commercial products, because their feature sets change frequently and their internals are not public.

Global aggregators. Platforms such as BookMyShow in South Asia and Fandango in North America aggregate listings from many cinema chains. They offer seat maps, wallets, offers and reviews. They are closed-source, integrate with each chain's ticketing back end, and charge per-ticket convenience fees. They are not available to a small Karachi venue as software it can run.

Cinema-chain websites. Large local chains run their own booking sites, typically built on commercial cinema management software that also drives the box office and the concession stand. These systems are comprehensive but proprietary and licensed per site, which places them out of reach of single-screen or small multi-screen cinemas.

Local ticket marketplaces. Pakistani marketplaces sell cinema tickets alongside bus, event and travel tickets, and support local payment methods such as JazzCash and Easypaisa. They depend on the participating cinema exposing its inventory.

Academic and open-source projects. Many freely available "online movie booking" projects written in PHP and MySQL are used as student templates. The baseline of this project belongs to this category. In our review of the baseline and of the pattern it represents, such projects usually record a booking as a single row with a seat count, build SQL by concatenating request values, store passwords and card numbers in plain text, and do not model shows or individual seats. They demonstrate CRUD operations but not the essential correctness property of a ticketing system.

2.3 Web application architecture

2.3.1 Client-server and three-tier architecture

Web applications conventionally follow a three-tier architecture: a presentation tier (the browser rendering HTML, CSS and JavaScript), an application tier (server code applying business rules) and a data tier (a database management system). The tiers communicate over HTTP and over a database protocol respectively. The separation allows each tier to be scaled and secured independently (Sommerville, 2016).

2.3.2 Server-side rendering and single-page applications

Two styles dominate the presentation tier. In server-side rendering (SSR), each URL is handled by server code that queries the database and returns a complete HTML page. In a single-page application (SPA), the browser downloads a JavaScript application once and exchanges JSON with a web API. SPAs give richer interaction at the cost of a separate API layer, a JavaScript build toolchain and more complex state management. SSR remains simpler to develop, to secure (no API surface beyond the pages) and to host.

CineMax Karachi uses SSR for all pages and adds small JSON endpoints only where interactivity requires it: seat holds, seat status polling, live search, promo validation and OTP issue. This hybrid keeps the benefits of SSR while providing an interactive seat map.

2.3.3 Enterprise application patterns

Fowler (2002) catalogues patterns for organising web application logic. Three of them describe CineMax Karachi precisely:

  • Page Controller. Each page is its own controller: seat_map.php handles the request for the seat map, checkout.php for checkout, and so on. This is the natural structure of a framework-less PHP site.

  • Transaction Script. Business operations are organised as procedures, each handling one request end to end, for example finalize_booking() and cancel_booking() in includes/booking.php. Fowler recommends Transaction Script for applications with modest domain logic, where a full Domain Model would add more structure than value.

  • Template View. Pages embed PHP in HTML markup to render data, as in partials/ticket_card.php.

Fowler also describes the Post/Redirect/Get discipline, in which a form submission is processed and then answered with an HTTP redirect, so that refreshing the result page does not resubmit the form. Our checkout, payment, cancellation and admin forms follow it.

The alternative would be a Model-View-Controller framework such as Laravel or Symfony. Section 2.4.1 explains why we did not migrate to one.

2.4 Technologies

2.4.1 PHP

PHP is a server-side scripting language designed for the web, with built-in session handling, form parsing and database drivers. It remains one of the most widely deployed server-side languages and is supported by nearly every shared hosting provider. The baseline system was written in procedural PHP, and the target deployment for a small cinema is inexpensive shared hosting. We therefore kept plain PHP rather than adopting a framework. A framework migration would have meant rewriting every existing page while delivering none of the missing booking features, and it would have raised the hosting requirements.

The system targets PHP 7.4 (the Docker image php:7.4-apache) and was also run end to end by the team on PHP 8.2 under XAMPP. The relevant language features are the mysqli extension with prepared statements, random_bytes() and random_int() for cryptographically secure tokens and OTPs, hash_equals() for constant-time comparison, and htmlspecialchars() for output encoding.

2.4.2 MariaDB and the InnoDB storage engine

MariaDB is a community-developed fork of MySQL, wire-compatible with it and used interchangeably in most hosting environments. Our environment runs MariaDB 10.4.34. All application tables use the InnoDB storage engine, which provides:

  • ACID transactions with BEGIN, COMMIT and ROLLBACK.

  • Row-level locking, including SELECT ... FOR UPDATE to lock rows read inside a transaction.

  • Unique and foreign-key constraints that are checked at write time regardless of the application code.

  • A default isolation level of REPEATABLE READ, with next-key locking to prevent phantoms in locking reads.

MariaDB-specific features we rely on are ADD COLUMN IF NOT EXISTS and ADD KEY IF NOT EXISTS, which make schema migrations safe to re-run.

2.4.3 Apache HTTP Server

Apache serves PHP through the mod_php module in the official php:7.4-apache image. We use its per-directory .htaccess support to deny script execution in the profile-photo upload directory, a standard defence against upload-based code execution.

2.5 Theoretical framework: concurrency control

2.5.1 Race conditions and the double-booking anomaly

A race condition occurs when the correctness of a computation depends on the relative timing of concurrent operations. The naive booking algorithm is a check-then-act sequence:

if seat E6 is free:        -- read
    record E6 as sold      -- write

If two requests execute the read before either executes the write, both see the seat as free and both sell it. This is the lost update or write skew family of anomalies described by Berenson et al. (1995). On a busy release night, the window between read and write, typically a few milliseconds, is wide enough for collisions to occur.

2.5.2 ACID transactions and isolation levels

A transaction groups operations so that they are Atomic (all or nothing), Consistent (constraints hold before and after), Isolated (concurrent transactions do not see each other's partial work) and Durable (committed work survives failure) (Gray and Reuter, 1992; Silberschatz, Korth and Sudarshan, 2019). The SQL standard defines four isolation levels, from READ UNCOMMITTED to SERIALIZABLE, by the anomalies each permits. Importantly, a plain read inside a REPEATABLE READ transaction does not lock the row it reads, so wrapping the naive check-then-act sequence in a transaction does not by itself prevent double booking. Additional measures are needed.

2.5.3 Pessimistic and optimistic control

There are three standard ways to make check-then-act safe (Elmasri and Navathe, 2016; Kleppmann, 2017):

  1. Pessimistic locking. Lock the resource before checking it, for example with SELECT ... FOR UPDATE, so a second transaction waits until the first commits.

  2. Optimistic concurrency control. Proceed without locks and detect conflicts at commit time, for example with a version column, retrying on conflict.

  3. Constraint-based exclusion. Let the database enforce the invariant directly through a UNIQUE constraint, so that the second insert of the same (show, seat) pair fails atomically. This collapses check and act into one indivisible operation.

The third approach is the most robust for seat booking because the invariant, "at most one sale per seat per show", maps exactly onto a unique key, and because it remains correct even if a future developer adds a new code path that forgets to lock. CineMax Karachi uses constraint-based exclusion as its primary guarantee and pessimistic locking (FOR UPDATE on the user's holds and on the promo code row) as a secondary measure inside the payment transaction.

2.5.4 Leases and expiring reservations

A hold is a lease: a grant of exclusive access that expires after a fixed time unless renewed or converted (Gray and Cheriton, 1989). Leases are a standard way to tolerate clients that disappear, such as a customer who closes the browser during checkout, without a separate clean-up protocol. Our holds carry an expires_at timestamp; expired holds are treated as free and are deleted lazily whenever seat state is read or written.

SQL injection arises when user input is concatenated into SQL text and changes the query's structure (Halfond, Viegas and Orso, 2006). Prepared statements send the query structure and the parameter values separately, so input can never be parsed as SQL.

Cross-site scripting (XSS) arises when user-controlled text is emitted into HTML without encoding and is interpreted as markup or script. The standard defence is to encode every dynamic value for the context it is written into; for HTML text and attributes this means htmlspecialchars() with ENT_QUOTES.

Cross-site request forgery (CSRF) occurs when a malicious site causes a victim's browser, which carries the victim's session cookie, to submit a state-changing request. The synchroniser token pattern defeats it: the server places a secret, unpredictable token in each form and rejects submissions that do not echo it, since the attacking site cannot read the token (Barth, Jackson and Mitchell, 2008).

Unrestricted file upload can lead to code execution if an uploaded file with a script extension is later served by the interpreter. Defences are allow-listing extensions, verifying content, renaming files and disabling execution in the upload directory.

2.7 QR codes for ticket verification

A QR code is a two-dimensional matrix barcode standardised in ISO/IEC 18004. It encodes text with Reed-Solomon error correction at four levels (L, M, Q, H), recovering roughly 7%, 15%, 25% and 30% of damaged codewords respectively. Our tickets use level M, a balance between density and tolerance for screen glare or a creased printout. A QR ticket should carry an opaque identifier rather than personal data, since anyone who photographs the ticket can read it. Validity must be decided by the server at scan time, so that a copied QR code is accepted only once. Signing the identifier with a key that only the server holds (a message authentication code such as HMAC) additionally lets anyone, not only the door scanner, recognise a code that the cinema did not issue.

2.8 Usability considerations

Nielsen's ten usability heuristics (Nielsen, 1994) informed the customer flow. Visibility of system status motivated the live seat-hold countdown and the ten-second seat-map refresh. Error prevention motivated disabling sold and held seats rather than reporting an error after the click, and the client-side card-format checks. Match between system and the real world motivated a seat map laid out like a hall, with the screen at the top and an aisle in the middle. Help users recognise, diagnose and recover from errors motivated messages such as "Sorry, E6 was just taken by someone else. Please choose other seats."

2.9 Summary and research gap

Commercial platforms solve double booking but are proprietary and costly. Freely available academic systems are affordable but omit the seat model and are insecure. The literature offers a clear set of techniques for closing that gap: database constraints and transactions for correctness, leases for abandoned checkouts, synchroniser tokens and prepared statements for security, and server-validated QR identifiers for admission. CineMax Karachi applies these techniques to a conventional, framework-less PHP and MariaDB stack, and evaluates whether the correctness guarantee holds under concurrent load.

3.4.2 UC-06 and UC-07: Book tickets (fully dressed)

Primary actor: Customer. Stakeholders and interests: the customer wants the chosen seats at the displayed price; the cinema wants each seat sold once and paid for. Preconditions: the show is Active and has not started; prices are set for the film. Trigger: the customer chooses a show time.

Main success scenario

  1. The system displays the seat map with current seat states and class prices.

  2. The customer selects one to ten free seats; the system shows a running total per class.

  3. The customer presses Continue.

  4. The system validates that every seat label exists in the hall, releases any earlier holds of this customer, and inserts a hold for each seat, expiring in five minutes.

  5. The system opens checkout with a hold countdown.

  6. The customer optionally adds snacks and applies a promo code; the system recomputes the total.

  7. The customer proceeds to payment, chooses a method and enters details.

  8. The system validates the details and, in one transaction, re-reads the customer's unexpired holds with a lock, re-validates the promo code with a lock, inserts the booking, assigns its reference, inserts one booking_seats row per seat, inserts snack lines, increments promo usage, adds loyalty points and deletes the holds.

  9. The system commits and shows the e-ticket with its QR code.

Extensions

  • 2a. The customer tries to select an eleventh seat: the system refuses and explains the limit.

  • 2b. During selection, polling reveals that a selected seat was taken: the system deselects it and names it.

  • 4a. A seat is already held or sold: the whole hold is rolled back and the conflicting seats are named; the customer chooses again.

  • 4b. The show has started or been cancelled: the system reports that the show is no longer available.

  • 5a. The countdown reaches zero: the system returns the customer to the seat map.

  • 6a. The promo code is unknown, inactive, expired or exhausted: a specific message is shown and no discount applies.

  • 8a. Payment details are invalid: the form is shown again with the error; the hold continues.

  • 8b. The hold expired before payment: the transaction is rolled back and the customer is returned to the seat map.

  • 8c. A seat insert violates the unique key: the transaction is rolled back and the customer is told which seat was taken.

Postconditions: exactly one booking exists with status Booked and refund status None; its seats are no longer selectable by anyone; the customer's holds are gone.

3.4.3 UC-10: Cancel booking

Preconditions: the booking belongs to the signed-in customer, has status Booked, and its show has not started.

  1. The customer presses Cancel on an upcoming booking.

  2. The system shows the refund quote: 100% if the show starts in 24 hours or more, otherwise 50%, floored to whole rupees.

  3. The customer confirms.

  4. The system verifies the CSRF token and ownership, then in one transaction sets status Cancelled, refund status Pending, the refund amount and the cancellation time (only if the status is still Booked), deletes the booking's seat rows and deducts the loyalty points, never below zero.

  5. The system shows the Cancelled tab with the pending refund.

Extensions: 4a. The status is no longer Booked (for example the ticket was scanned in the meantime): nothing changes and the customer is told the booking can no longer be cancelled.

3.4.4 UC-16: Scan ticket

  1. Door staff open the scanner and start the camera, or type a reference.

  2. The scanner reads the QR code and submits its content, a signed link, with the session's CSRF token.

  3. The system atomically changes status from Booked to Used and records the check-in time, and reports VALID with booking details.

  4. If no row changed, the system reports ALREADY_USED, CANCELLED or NOT_FOUND according to the booking's state. A code whose signature does not match its reference is reported as FORGED, and a genuine unused ticket for another day as WRONG_DAY; neither is checked in.

3.6 Feasibility study

Technical feasibility. Every requirement maps onto standard features of PHP 7.4+ and InnoDB: sessions, prepared statements, transactions, unique keys and row locks. No component requires specialised infrastructure. The highest-risk requirement, NFR-01, can be met with a unique key, which the database enforces regardless of load.

Economic feasibility. All software used is free and open source, and TMDB is free for non-commercial use. A production deployment needs only a PHP and MySQL host, available in Pakistan at low monthly cost, plus a payment-gateway merchant account at the operator's expense.

Operational feasibility. Cinema staff already understand shows, halls and seat classes, so the admin panel uses the same vocabulary. The scanner runs in a phone or laptop browser and needs no dedicated hardware.

Schedule feasibility. The work was divided into a shared foundation step followed by five feature phases for the core booking engine, with the admin and customer-account pages developed in parallel under a file-ownership model (Section 5.1). The repository history shows the foundation, the five core phases, four administration and account tasks, the TMDB integration and the final test fixes all completed within the project timeline.

Chapter 4: System Architecture and Design

CineMax Karachi is a server-rendered, three-tier web application: browsers talk HTTP to Apache and PHP, PHP talks to a single MariaDB database, and an offline command-line seeder talks to the TMDB API. This chapter describes the architecture, the database schema and its evolution, the key workflows and state machines, and the design decisions behind them.

4.1 Architectural overview

Figure 4.1 shows the runtime components and how they call each other.

Figure 4.1: Runtime architecture. Browsers call page controllers and AJAX endpoints over HTTP; every one of them goes through the helper layer to MariaDB, and only the command-line seeder talks to TMDB.

The system has two web applications that share one database and one helper layer:

  • The customer site (repository root) consists of page controllers such as index.php, moviedetail.php, select_show.php, seat_map.php, checkout.php, payment.php, ticket.php, userbooking.php and cancel_booking.php. Each page includes header.php and footer.php for the shared layout and navigation.

  • The admin panel (Admin/) consists of one page per feature. Every page begins with include('auth.php'), which redirects to login.php unless an administrator is signed in, and then includes admin_header.php, which renders the sidebar and loads the helper layer.

  • The helper layer (includes/) holds all shared logic. functions.php provides database access, escaping, CSRF tokens, flash messages, redirects and the current user. booking.php holds the booking domain: seat classes, holds, prices, totals, promotions, booking, cancellation and refunds. admin_functions.php provides the activity log. tmdb.php is the TMDB HTTP client.

  • AJAX endpoints (ajax/) return JSON for the interactive parts of the customer site: seat_hold.php, seat_status.php, search.php, promo.php and payment_otp.php.

  • Partials (partials/) are reusable view fragments: the movie browser, show list, ticket card, hold timer, home slider and coming-soon strip.

  • Database tooling (database/) holds the numbered migrations, the schema contract, the TMDB seeder and a demo-data seeder. The seeders refuse to run over HTTP and run only from the command line.

4.3 Request lifecycle

A typical state-changing request, such as a customer cancelling a booking, flows as follows:

  1. The browser POSTs the form, including the hidden csrf field, to cancel_booking.php.

  2. The page includes includes/booking.php, which includes functions.php, which includes config.php (opening the mysqli connection), starts the session if needed, sets the PHP time zone to Asia/Karachi and issues SET time_zone = '+05:00' on the connection.

  3. require_login() redirects to signin.php if no customer is signed in, remembering the requested URL.

  4. The controller rejects the request unless it is a POST with a valid CSRF token.

  5. load_booking() fetches the booking by reference with a prepared statement; owns_booking() confirms that it belongs to the current user.

  6. cancel_booking() runs the transaction.

  7. The controller stores a flash message in the session and redirects to userbooking.php?tab=cancelled.

  8. The browser follows the redirect with a GET; the page renders and displays the flash message once.

4.4.6 Normalisation and deliberate denormalisation

The new tables are in third normal form: each non-key attribute depends only on its table's key. Two departures are deliberate.

  1. Snapshot columns on booking_details. A booking records the film name, cinema, date, time and seat-class summary as text at the time of sale. If an administrator later renames a film, changes a price or deletes a past show, the customer's ticket and the revenue reports still show what was actually sold. This is the standard treatment of transactional records, comparable to an invoice that copies the product description and price. booking_seats.price and booking_snacks.price follow the same principle.

  2. Derived totals. total_amount, snacks_amount and discount_amount could be recomputed from the line tables, but they are stored so that legacy bookings, which have no line rows, report consistently.

One inherited weakness was kept for compatibility and is listed as future work: movie_price is joined to films by name rather than by movie_id, and stores prices as text.

4.5 Seat model

A hall is a rectangle of total_rows × seats_per_row seats, 8 × 12 = 96 by default. Rows are lettered from A and seats numbered from 1, so labels run from A1 to H12. The class of a seat is a pure function of its row letter:

index = ord(row) - ord('A')
class = Economy   if index < 3      (rows A-C)
        Business  if index < 6      (rows D-F)
        First     otherwise         (rows G onward)

The seat map inserts an aisle after seat ceil(seats_per_row / 2). Validation (valid_seat_label()) accepts a label only if it matches ^[A-Z][0-9]{1,2}$, its row is within the hall's rows and its number is between 1 and seats_per_row.

A seat's state for a given show is derived, not stored: it is sold if a booking_seats row exists, held by me or held by another if an unexpired seat_holds row exists, and free otherwise. Deriving the state from the two tables at read time means there is no separate status column that could drift out of agreement with them.

4.6 Booking workflow

Figure 4.3 traces the interactions from seat selection to e-ticket.

Figure 4.3: Booking sequence. Solid arrows are requests, dashed arrows replies; the two highlighted writes are the points where a UNIQUE (show_id, seat_label) key can refuse a seat. Selection and checkout write nothing to the seat tables.

The workflow has three phases with different consistency needs:

  1. Selection (no writes). The customer selects seats in the browser. The page polls seat_status.php every ten seconds and disables seats that others have taken, but nothing is reserved. This keeps browsing cheap and avoids locking seats for customers who are only looking.

  2. Hold (short transaction). Continue sends the selection to seat_hold.php. In one transaction the server deletes the customer's previous holds, checks each seat against booking_seats, and inserts a hold. Any failed insert, including a unique-key violation caused by a concurrent customer, rolls back the whole hold. The customer therefore gets all the requested seats or none.

  3. Commit (one transaction). On payment, finalize_booking() re-reads the customer's unexpired holds FOR UPDATE, re-validates the promo code FOR UPDATE, and writes the booking, reference, seat rows, snack rows, promo usage and loyalty points, then deletes the holds and commits. The booking_seats unique key is the final guard: even if a hold had somehow been lost, a duplicate sale would fail and roll back.

5.4 The helper layer

The baseline had no shared code beyond the connection file. The first increment introduced includes/functions.php, which every new page includes. Including it has three side effects that establish a consistent runtime: it opens the database connection, starts the session if one is not already active, and aligns PHP and MySQL on the Asia/Karachi time zone.

require_once __DIR__ . '/../config.php';

if (session_status() === PHP_SESSION_NONE) {
    session_start();
}

date_default_timezone_set('Asia/Karachi');
mysqli_set_charset($con, 'utf8mb4');
mysqli_query($con, "SET time_zone = '+05:00'");

Aligning both clocks matters because business rules mix PHP time and SQL time: holds expire by SQL NOW(), while refund quotes compare a show's start with PHP time(). In the Docker container the server clock is UTC, so without these lines a show at 18:30 Karachi time would be judged five hours wrong.

5.4.1 Prepared-statement wrapper

db_query() is the single entry point for parameterised SQL. It prepares the statement, binds parameters by type string (i integer, s string, d double) and returns a result set for reads, the affected-row count for writes, or false on any failure.

function db_query($sql, $types = '', $params = [])
{
    $stmt = mysqli_prepare(db(), $sql);
    if (!$stmt) {
        return false;
    }
    if ($types !== '') {
        mysqli_stmt_bind_param($stmt, $types, ...$params);
    }
    if (!mysqli_stmt_execute($stmt)) {
        mysqli_stmt_close($stmt);
        return false;
    }
    $result = mysqli_stmt_get_result($stmt);
    if ($result === false) {
        $affected = mysqli_stmt_affected_rows($stmt);
        mysqli_stmt_close($stmt);
        return $affected;
    }
    mysqli_stmt_close($stmt);
    return $result;
}

db_one() and db_all() wrap it to return one associative row or all rows. Returning the affected-row count is what makes the conditional state transitions of Section 4.7 possible: callers test === 1 to learn whether their guarded UPDATE took effect. Across the codebase there are 223 calls to these three helpers, against 22 remaining raw mysqli_query() calls in legacy admin listing pages, none of which interpolate request input.

5.4.2 Output escaping, CSRF tokens and messages

function e($value)
{
    return htmlspecialchars((string) $value, ENT_QUOTES, 'UTF-8');
}

function csrf_token()
{
    if (empty($_SESSION['csrf'])) {
        $_SESSION['csrf'] = bin2hex(random_bytes(16));
    }
    return $_SESSION['csrf'];
}

function csrf_ok()
{
    return isset($_POST['csrf']) && hash_equals(csrf_token(), (string) $_POST['csrf']);
}

The CSRF token is 128 bits from the operating system's cryptographic random source, stored in the session and rendered into forms by csrf_field(). hash_equals() compares in constant time, so response timing does not leak how many leading characters matched. flash() stores a one-time message in the session and render_flash() prints and clears it, which is how a redirect can carry "Booking CNX-2026-00051 cancelled" to the next page.

current_user_id() returns the signed-in customer's id from the session, falling back to a lookup by email for sessions created by legacy pages. require_login() remembers the requested URL in $_SESSION['after_login'] and redirects to sign-in. 5.6.2 The hold transaction

function hold_seats($show_id, $user_id, $labels)
{
    release_expired_holds();
    mysqli_begin_transaction(db());
    db_query('DELETE FROM seat_holds WHERE user_id = ?', 'i', [(int) $user_id]);
    $conflicts = [];
    foreach ($labels as $label) {
        $booked = db_one('SELECT 1 FROM booking_seats WHERE show_id = ? AND seat_label = ?', 'is', [(int) $show_id, $label]);
        $inserted = $booked ? false : db_query(
            'INSERT INTO seat_holds (show_id, seat_label, user_id, expires_at) VALUES (?, ?, ?, NOW() + INTERVAL ' . HOLD_MINUTES . ' MINUTE)',
            'isi',
            [(int) $show_id, $label, (int) $user_id]
        );
        if (!$inserted) {
            $conflicts[] = $label;
        }
    }
    if ($conflicts) {
        mysqli_rollback(db());
        return $conflicts;
    }
    mysqli_commit(db());
    return [];
}

Three properties of this function matter.

  1. One active selection per customer. Deleting the customer's existing holds first means a customer who goes back and picks different seats does not keep the old ones locked.

  2. The unique key decides contention. If two customers race for seat H12, both may pass the booking_seats check, but only one INSERT INTO seat_holds can succeed, because of UNIQUE (show_id, seat_label). The loser's insert fails, db_query() returns false, and the seat is reported as a conflict.

  3. All or nothing. Any conflict rolls back the whole transaction, including the deletion of the customer's earlier holds, so a failed attempt leaves the customer exactly where they were.

5.6.3 Expiry

Holds are never extended. release_expired_holds() runs DELETE FROM seat_holds WHERE expires_at <= NOW() at the start of every seat read and every hold attempt, using the idx_hold_expiry index. A hold that expires therefore frees its seat for the very next reader, without a scheduler. The checkout and payment pages show the remaining time, computed by SQL as TIMESTAMPDIFF(SECOND, NOW(), expires_at), through the partials/hold_timer.php countdown, which returns the customer to the seat map when it reaches zero.

5.8 Payment simulation

Real payment processing was out of scope, but the payment step was built to behave like one so that the booking transaction is exercised realistically and the integration point for a real gateway is clear.

Card. The browser formats the card number in groups of four and the expiry as MM/YY, and checks the format before submitting. Only substr($number, -4) is passed on to the booking. The CVV field is a password input and the CVV is never stored.

5.9 Booking finalisation

finalize_booking() is the most important function in the system. It turns a customer's holds into a confirmed booking in a single transaction, and every failure path rolls back.

function finalize_booking($user, $show, $snack_qty, $promo_code, $method, $account_last4)
{
    $db = db();
    mysqli_begin_transaction($db);

The design choices in this function are:

  • Holds are the source of truth for which seats are being bought. The seats are re-read from seat_holds inside the transaction, not taken from the form. A customer cannot add seats to the order by editing the request.

  • Prices and totals are recomputed inside the transaction. If an administrator changes a price between checkout and payment, the customer pays the price at the moment of commit, and the ticket shows that price.

  • Two locks, one invariant. FOR UPDATE on the holds and on the promo row serialises concurrent attempts by the same customer and concurrent redemptions of a limited code. The booking_seats unique key remains the final guarantee that no seat is sold twice.

  • The reference is derived from the auto-increment id inside the same transaction, so it is unique and gap-free per booking without a separate sequence. generate_booking_ref(51) in 2026 yields CNX-2026-00051.

  • The booking row stores snapshots of the customer name and email, film, cinema, date, time, seat labels and class summary, as described in Section 4.4.6.

payment.php calls finalize_booking() after validating the payment details. On success it clears the checkout state and OTP from the session and redirects to booking_success.php?ref=.... On failure it re-checks whether the holds still exist: if so the payment form is shown again with the error, otherwise the customer is sent back to the seat map.

5.10.1 Signed QR codes and public verification

An early version of the ticket encoded only the booking reference, for example CNX-2026-00051. The door scanner could look that reference up, but any other phone showed just the text, and nothing on the ticket proved that the cinema had issued it: anyone could print a QR code containing a made-up reference. The final version makes the QR code itself verifiable.

The QR code now encodes a link to the public verification page, carrying the reference and a signature:

https://<site>/verify.php?ref=CNX-2026-00059&sig=f20c1c621501b1df8fe48130

The signature is a keyed hash (HMAC-SHA256) of the reference, computed with a 64-character secret that exists only on the server (ticket_secret in includes/secrets.php, or the TICKET_SECRET environment variable), and shortened to 24 hexadecimal characters (96 bits):

function ticket_signature($ref)
{
    return substr(hash_hmac('sha256', strtoupper(trim((string) $ref)), ticket_secret()), 0, 24);
}

function ticket_signature_ok($ref, $sig)
{
    return is_string($sig) && $sig !== '' && hash_equals(ticket_signature($ref), strtolower($sig));
}

Without the secret, nobody can produce a valid signature for a reference, and changing any character of the reference invalidates the signature. hash_equals() compares in constant time, so response timing reveals nothing about how close a guess was.

Scanning the QR code with any phone camera opens verify.php, which shows one of five verdicts: Genuine ticket, Already used (with the check-in time), Cancelled ticket, Show date has passed, or Not a valid CineMax ticket. For a genuine ticket it shows the movie, cinema, hall, date, time, booking reference and seats with their classes. The customer's name is masked ("Ayesha Khan" becomes "A***** K***") and no email address, phone number or price is shown. The page reveals nothing when the signature is missing or wrong, so booking references cannot be enumerated by guessing. Verification is read-only: only the admin scanner can admit a ticket.

function refund_quote($booking)
{
    if ($booking['status'] !== 'Booked' || !$booking['starts_at']) {
        return null;

    $seconds = strtotime($booking['starts_at']) - time();
    if ($seconds <= 0) {
        return null;

}

5.16 TMDB integration

5.16.1 The API client

includes/tmdb.php is a small cURL-based client. tmdb_key() reads the key from the TMDB_API_KEY environment variable or, failing that, from includes/secrets.php. tmdb_get() detects the credential type: a v4 read-access token (a JWT beginning eyJ) is sent as an Authorization: Bearer header, a v3 key as an api_key query parameter. It retries up to three times on HTTP 429, any 5xx status or a network failure, sleeping 1 and then 2 seconds between attempts (linear back-off), and raises an exception with TMDB's status_message on other errors.

tmdb_trailer_key() chooses the best YouTube video for a film by scoring each candidate: 4 points for type Trailer, 2 for Teaser, plus 1 if TMDB marks it official. tmdb_download() fetches an image and rejects responses that are not HTTP 200 or are smaller than 1 KB, a heuristic for error pages.

5.16.2 The seeding algorithm

database/seed_tmdb.php replaces the catalogue with current data. It runs only from the command line (it returns 404 over HTTP) and does nothing without the --yes flag except print instructions and a backup command.

1. Preconditions: upload directory writable; migration 005 applied; at least one cinema.
2. Fetch TMDB's genre list.
3. Collect candidate films, skipping adult titles, titles without posters and duplicates:
     Hollywood: /movie/now_playing (region US), English, released in the last 120 days   -> 16
     Bollywood: /discover/movie, original language Hindi, last 150 days, by popularity   -> 8
     Lollywood: /discover/movie, origin country PK, last 3 years, by popularity          -> 6
     Coming soon: /movie/upcoming (region US), release date after today                 -> 8
4. For each film, fetch details with videos; download poster (w500) and backdrop (w1280).
   Skip films whose poster download fails.
5. If fewer than 3 films were downloaded, stop: the database is untouched.
6. Sort films by popularity. BEGIN TRANSACTION.
7. Delete holds, booking seats, booking snacks, bookings, reviews, favourites, shows,
   prices, coming soon and films. Reset promo usage and loyalty points.
8. For each film (rank r):
     map original language and origin country to an industry (PK -> LollyWood,
       en -> HollyWood, hi -> BollyWood, ...);
     look up or create genre, language and release-date rows;
     insert the film with TMDB id, backdrop, rating, runtime, popularity, trailer URL;
     price tier by rank: r < 5 -> 1500/2100/2900; r < 15 -> 1200/1700/2400; else 1000/1400/2000;
     create 4 shows (r < 10) or 3 shows over the next 7 days at rotating times
       (13:00, 15:45, 18:30, 21:15, 23:30), cinemas and halls, never within the next hour.
9. Insert coming-soon rows. Delete genres, languages and dates no film uses.
10. Log the seeding in activity_log. COMMIT (or ROLLBACK on any exception).
11. Reset auto-increment counters of the booking tables; delete stale tmdb_* images.

Three properties make the seeder safe to run before a demonstration. All network work happens before the transaction, so a TMDB outage leaves the database untouched. The database work happens in one transaction, so a failure part-way through rolls back completely. And the seeder refuses to proceed with a nearly empty result, so a bad API response cannot wipe the catalogue.

The popularity-based price tiers mean the most popular new releases cost more, a simple model of demand-based pricing. The resulting catalogue in our environment held 30 films (16 Hollywood, 8 Bollywood, 6 Lollywood), 8 coming-soon titles and 112 shows across 9 cinemas.

Chapter 6: Risk Management and Mitigation

The highest-impact risk in this project, selling one seat twice, was mitigated by design and verified by test; the largest residual risks are plain-text password storage and the simulated payment step, both of which are documented and scheduled as future work. This chapter describes how risks were identified and scored, then covers project, technical and security risks in turn, and ends with the residual-risk register.

6.1 Approach

Risks were identified at three points: during the audit of the baseline system, at the start of each increment ("what could this change break?"), and during the end-to-end test passes. Each risk was scored on a 1 to 5 scale for likelihood (L) and impact (I); the product L × I gives an exposure from 1 to 25. Exposures of 15 or more were treated as high and had to be mitigated before the increment was merged; 8 to 14 as medium, mitigated or explicitly accepted; below 8 as low, monitored.

Mitigations were recorded where developers would see them: in TEAM_NOTES.md (ownership, requests, known bugs), in database/SCHEMA_CONTRACT.md (rules), and in VIVA_PREP.md (limitations, stated honestly).

6.3 Technical risks

6.3.1 Double booking under concurrency (high, mitigated)

This was the defining technical risk (L 4, I 5, exposure 20). On a release night, many customers select the same central seats within seconds of each other. A check-then-insert implementation would sell some seats twice.

Mitigation. Three independent layers, described in Sections 4.6 and 5.6: unique keys on (show_id, seat_label) in both seat_holds and booking_seats; all-or-nothing hold transactions; and a booking transaction that re-reads holds FOR UPDATE. The layers are independent: removing any one still leaves the unique key on booking_seats, which on its own prevents a duplicate sale.

Verification. Section 7.5 reports a test in which ten authenticated users requested the same seat simultaneously, repeated for 21 seats (1 + 20 rounds, 210 requests). Every round produced exactly one successful hold and nine refusals.

6.3.2 Abandoned checkouts locking seats (medium, mitigated)

If holds never expired, a customer who closed the browser would block seats indefinitely (L 5, I 3, exposure 15). Mitigation: holds are leases with a five-minute expiry; expired holds are deleted on every read and write of seat state; a customer has at most one active selection, because a new hold replaces the previous one; and the checkout countdown returns the customer to the seat map at expiry.

6.3.3 Partial writes (high, mitigated)

A booking touches six tables. A failure halfway through could leave a paid booking without seats, or seats without a booking (L 2, I 5, exposure 10). Mitigation: one InnoDB transaction with a single failure path ($fail) that rolls back. The TMDB seeder applies the same rule to its catalogue replacement, and performs all network calls before opening its transaction.

6.3.4 Time-zone errors (medium, mitigated)

The Docker host runs on UTC while the business operates in Pakistan Standard Time (UTC+5). Hold expiry, show visibility and the 24-hour refund rule would be wrong by five hours if PHP and MySQL disagreed (L 4, I 3, exposure 12). Mitigation: the helper layer sets both the PHP time zone and the MySQL session time zone on every request. Times are compared in SQL where possible, using TIMESTAMP(show_date, show_time) > NOW().

6.3.5 Legacy data compatibility (medium, mitigated)

Old bookings have no show, seats or totals. Reports and the dashboard could crash or miscount (L 4, I 2, exposure 8). Mitigation: migration 001 backfills totals, references and user ids; the dashboard's TICKETS_SQL expression counts tickets correctly for both formats; ticket pages fall back to the snapshot text when no show exists.

6.3.6 External API dependency (medium, mitigated)

TMDB could be unreachable, rate-limit the seeder, or return unexpected data (L 3, I 3, exposure 9). Mitigation: the website never calls TMDB at request time; all images are downloaded and served locally. The seeder retries on 429 and 5xx, refuses to proceed with fewer than three films, and rolls back on any error.

6.3.7 PHP version differences (medium, partially mitigated)

The team ran Docker with PHP 7.4 and XAMPP with PHP 8.2. From PHP 8.1, mysqli throws mysqli_sql_exception by default instead of returning false (L 4, I 3, exposure 12). Under PHP 8.2, a duplicate-key failure in hold_seats() therefore raises an uncaught exception, and the customer sees a PHP error page instead of "Sorry, C9 was just taken". The double booking is still prevented, because the unique key rejected the insert and the transaction is never committed, but the user experience is wrong.

Status: reported in TEAM_NOTES.md with a one-line fix, not yet applied. The fix is either to call mysqli_report(MYSQLI_REPORT_OFF) once in the helper layer, or to wrap mysqli_stmt_execute() in db_query() in a try ... catch (mysqli_sql_exception $e) that returns false. Our Docker tests ran on PHP 7.4, where the friendly message appears (Section 7.5).

6.3.8 Performance under load (low, accepted)

Pages run a modest number of queries, and the hottest endpoint, seat-status polling, runs three indexed queries. Section 7.6 shows comfortable throughput on one host. One known inefficiency, the legacy admin film list issuing five lookup queries per film (an N+1 pattern), affects only an administrator page and is accepted.

6.4.2 Residual security risks

The following weaknesses remain. We list them explicitly because a system that will hold customer data must not hide them.

  1. Plain-text passwords (high). Customer and administrator passwords are stored and compared as plain text, inherited from the baseline. Anyone with read access to the database, or to a backup, learns every password, and users who reuse passwords are exposed elsewhere. Remedy: store password_hash($password, PASSWORD_DEFAULT) (bcrypt) and check with password_verify(); migrate each existing user transparently at their next successful login; then remove the plain-text values.

  2. No CSRF token on the checkout and payment steps (medium). checkout.php, payment.php and the AJAX endpoints seat_hold.php, promo.php and payment_otp.php accept POSTs without a token. Because payment is simulated, a forged request could at worst create holds or a booking on the victim's own account using details the attacker would have to supply, but the gap is inconsistent with the rest of the system. Remedy: add csrf_field() to the forms and send the token in a request header from the fetch() calls.

  3. Customer session fixation (medium). Administrator login calls session_regenerate_id(true), but customer sign-in does not. An attacker who can plant a session identifier in a victim's browser could share the victim's session after login. Remedy: one call to session_regenerate_id(true) after successful customer sign-in, plus HttpOnly, Secure and SameSite=Lax cookie flags in production.

  4. No login throttling (medium). Neither login form limits failed attempts. Remedy: count failures per account and per IP address with a short lock-out, or add a CAPTCHA after several failures.

  5. Demonstration OTP returned to the browser (accepted for demo). The OTP endpoint returns the code so the demonstration can proceed without an SMS gateway. In production the code must be sent only by SMS.

  6. API key in the private repository (accepted, controlled). The TMDB key is committed in includes/secrets.php so that each developer can seed a database; the repository is private, an environment variable overrides the file, and the team notes require deleting the file from history and regenerating the key before the repository is ever made public.

  7. Development database configuration (accepted for development). The database root account has an empty password and the SQL mode is permissive. These settings exist only for local development and must be changed for any deployment.

6.5 Data protection and privacy

The system processes personal data: names, email addresses, phone numbers, profile photos and booking history. Pakistan's draft Personal Data Protection Bill and general good practice suggest the following controls, several of which are already in place: data minimisation (only the last four digits of payment accounts; the QR code holds only the booking reference and its signature, and the public verification page masks the customer's name); purpose limitation (customer data is used only for bookings and the customer's own account); access control (customers see only their own bookings; administrators require authentication); and accountability (the activity log). Password hashing (6.4.2 item 1) and HTTPS in production are the most important remaining controls.

Chapter 8: Future Scope and Conclusion

The system is ready to demonstrate and its booking engine is sound; making it ready for paying customers requires four security fixes and a real payment gateway, after which it can grow toward multiple cinemas, mobile clients and higher load. This chapter sets out that path in priority order and then concludes the report.

8.1 Immediate improvements (before any production use)

These changes close the residual risks of Section 6.6. Each is small and local.

  1. Password hashing. Replace plain-text storage with password_hash() and password_verify(). A transparent migration avoids forcing resets: at sign-in, if the stored value is not a hash and matches the typed password, re-store it as a hash.

$user = db_one('SELECT id, name, email, password, status FROM user_reg_login WHERE email = ? LIMIT 1', 's', [$email]);
$ok = $user && (password_verify($password, $user['password'])
    || (strpos($user['password'], '$2y$') !== 0 && hash_equals($user['password'], $password)));
if ($ok && password_needs_rehash($user['password'], PASSWORD_DEFAULT)) {
    db_query('UPDATE user_reg_login SET password = ? WHERE id = ?', 'si', [password_hash($password, PASSWORD_DEFAULT), $user['id']]);
}

  1. Exception-safe data access. Make db_query() return false on mysqli_sql_exception so that PHP 8.1+ shows the intended "seat was just taken" message.

  2. CSRF everywhere. Add tokens to checkout.php and payment.php, and send the token in an X-CSRF-Token header from every fetch() call, checked by the AJAX endpoints.

  3. Session hardening. Regenerate the session id at customer sign-in; set HttpOnly, Secure and SameSite=Lax on the session cookie; serve the site only over HTTPS.

  4. Login throttling. Lock an account or IP address for a few minutes after repeated failures.

  5. Production configuration. A non-root database user with a strong password and only the privileges the application needs; strict SQL mode once the legacy pages are verified against it; error display off; secrets only in environment variables.

  • Store show start as a single DATETIME column instead of a DATE and a HH:MM string, which would let the database index show-time comparisons.

8.4 Scalability

The current deployment is a single web container and a single database. Section 7.7 suggests this already serves several thousand simultaneous seat-map viewers. Growth beyond that follows a well-known path, and the design choices made so far keep it open:

  1. Stateless web tier. Move PHP sessions from local files to Redis or the database. The web containers then become interchangeable and can run behind a load balancer. The holds already live in the database, not in sessions, so they work across servers without change.

  2. Cache read-heavy pages. Film listings and detail pages change only when an administrator edits the catalogue; they can be cached for seconds to minutes. Seat state must not be cached, but its endpoint is already cheap.

  3. Push instead of poll. Replace the ten-second poll with server-sent events or WebSockets fed by a lightweight pub/sub channel, reducing request volume and making seat changes visible within a second.

  4. Database scaling. Read replicas can serve listings and reports. The booking transaction must stay on the primary, and because each show's seats are independent, the write load can later be partitioned by show or by cinema if a single primary is ever insufficient.

  5. Background work. Move report generation, emails and the TMDB seeding to a job queue.

  6. Observability. Structured logs, request timing and alerts on booking failures and payment callback errors.

The central invariant does not change at any step: whatever serves the request, the unique key on (show_id, seat_label) in the primary database decides who gets the seat.

8.5 Mobile and API

The AJAX endpoints already form a small JSON API for seats, holds, search and promotions. Adding endpoints for authentication (with tokens instead of cookies), shows, checkout and tickets would let a mobile app or a progressive web app reuse the same booking engine. A PWA could store tickets offline so that the QR code is available at the cinema entrance without a network connection.

8.6 Engineering practice

  • Automated tests. Turn the 22 unit checks and the integration and concurrency scripts of Chapter 7 into a PHPUnit suite and a CI job that runs them against a containerised database on every push.

  • Static analysis. PHPStan or Psalm at a low level would catch type errors and undefined variables in legacy pages.

  • Finish the migration to prepared statements in the 22 remaining legacy mysqli_query() calls, and remove the N+1 queries in the admin film list with joins.

  • Accessibility. Descriptive aria-labels on seats and non-colour cues for seat state.

8.7 Lessons learned

  1. Put invariants in the database. The most valuable line in the project is a unique key. Application checks can be bypassed by a new code path, a race or a PHP upgrade; a constraint cannot.

  2. Design for the abandoned customer. Most checkouts that start do not finish. Expiring holds made abandonment a non-event instead of a support problem.

  3. Small helpers go a long way. A 145-line helper file supplied most of what a framework would have provided for safety (prepared statements, escaping, CSRF, flash messages, redirects), without rewriting the legacy pages.

  4. Migrations and contracts make teamwork possible. Re-runnable migrations and a written schema contract let two developers change the same database in parallel. The one incident, migration 001 breaking column-less INSERTs, was caught and fixed within a day because the request process made it visible.

  5. Measure, then claim. The concurrency test turned "we use a unique key" into "21 of 21 races produced exactly one winner", and the performance test revealed the session-locking effect, which code review alone would have missed.

  6. Be honest about limits. Recording known weaknesses (plain-text passwords, demo payment) in the team's own documents kept them visible and made this report's risk register straightforward to write.

8.8 Conclusion

This project set out to turn a minimal, insecure academic booking site into a seat-level cinema ticketing system for Karachi that can be trusted not to sell a seat twice, using only conventional, low-cost technology: plain PHP, MariaDB and server-rendered pages.

The resulting system, CineMax Karachi, covers the full ticket lifecycle. Customers browse a catalogue of real current films from TMDB, choose a show, pick exact seats on a live map, add snacks and promotions, pay through a simulated card or mobile-wallet step, and receive a QR e-ticket, which they can cancel under a clear refund policy. Staff schedule shows with clash detection, manage prices, snacks, promotions and users, approve refunds, admit customers with a camera scanner, and follow sales on a dashboard with exportable reports.

The core technical contribution is the concurrency design: expiring holds stored in the database, unique keys on (show_id, seat_label) for both holds and sold seats, and a single transaction for each booking. Evaluation confirmed it: in 21 rounds of ten simultaneous requests for the same seat, exactly one request won every time, while all 22 business-rule checks and the end-to-end, scanning, cancellation and access-control tests behaved as specified, and public pages responded within 112 ms at the 95th percentile under ten concurrent clients.

The work also shows how an inherited codebase can be improved safely: by leaving the original dump untouched, delivering every schema change as a re-runnable migration, introducing a small shared helper layer, and dividing ownership clearly between developers.

The system is not yet ready to take real money. Passwords must be hashed, CSRF protection extended to the checkout endpoints, sessions hardened, and the simulated payment replaced with a gateway confirmed server to server. These are well-understood, bounded tasks. With them completed, CineMax Karachi would offer a small Karachi cinema what has so far been available mainly to large chains: online, seat-level booking that customers can rely on, on infrastructure the cinema can afford.
